## Why the version did NOT move

The instruction was "bump to 0.2.3 — but if bumping implies a release, stay at
0.2.2 and record the tip commit instead". It implies one.

The release *workflow* is tag-gated (`release-windows.yml`, `tags: ["v*"]`), so a
bump alone fires nothing. But in this repo a version on `main` **means a shipped
version**: it lands as its own "Release vX.Y.Z" PR, `test_version_single_source`
pins it across 9 sites, and the Windows installer builds from `v*` tags named for
exactly those numbers. Burning 0.2.3 on a local build for one run would make the
number claim a release that never happened, and would collide with the real 0.2.3.

So the tip commit is the identity, and the log filename carries it — this build is
`2026-09-04_0.2.2_67a8b74`, the previous one `2026-09-03_0.2.2_4c20a93`. Two builds
of "0.2.2" that remain tellable apart.
